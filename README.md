# 计时器

一个用 Python + Tkinter 写的桌面计时器（秒表 + 倒计时）。计时逻辑与界面代码分成两层，运行时零第三方依赖。

---

## 一、功能

- 大号数字显示区，格式为 `时:分:秒`，启动时显示 `00:00:00`
- 三个按钮：**开始** / **重置** / **切换为倒计时**；计时中"开始"就地变成**暂停**（同一颗按钮，不用来回找）
- **半透明深灰面板**：整块窗口是圆角的深灰色，能透出底下的软件，但数字和按钮依然清楚
- **整块都能拖**：面板上没有一处是"点不动"的，随便抓哪里都能移动窗口
- **四边四角都能拉大小**：鼠标移到任意一条边或一个角，指针变成对应的双箭头，拖就改尺寸；字跟着缩放，不会变形
- **倒计时真的能用**：点数字弹框设时长，数到 0 响铃、面板闪烁、弹提示；两种模式各自记着自己的状态
- **窗口置顶**：默认浮在其他程序之上，按 `T` 键切换
- **无边框窗口**：没有系统标题栏和边框，右上角只有一个小小的 ×
- **记住设置**：窗口大小、位置、上次用的模式、上次设的倒计时时长，下次打开都还在
- **计时中关窗会二次确认**，防止手滑关掉正在跑的计时
- 第一次启动时自动出现在屏幕中央
- 支持键盘快捷键操作

## 二、项目结构

> **只要运行 `timer.py` 就行。** 其他 `.py` 都是它拆出来的零件，不能单独运行，你平时不需要打开它们。

```
DesktopTimer/
├─ timer.py           入口 —— 双击或运行的就是它
├─ timer_core.py      【后端】只管时间怎么算
├─ timer_view.py      【算法】只管颜色、字号、窗口尺寸怎么算
├─ timer_settings.py  【记忆】只管把设置存到磁盘、再读回来
├─ timer_ui.py        【前端】只管窗口长什么样
├─ tests/             自动检查程序对不对的代码，平时用不到
├─ README.md
└─ .gitignore
```

### 为什么从一个文件变成了五个

原来是**一个** `timer.py`，167 行，时间计算和窗口绘制全混在一起。现在按职责拆开：

| 文件 | 你的说法 | 只管什么 | 能单独运行吗 |
| --- | --- | --- | --- |
| `timer_core.py` | **后端** | 时间：秒表（开始、暂停、继续、归零）+ 倒计时（设时长、倒数、到点），读数与格式化 | 不能，它没有界面，运行起来什么都不显示 |
| `timer_view.py` | **算法** | 面板颜色、字号、窗口尺寸、按钮摆位、四边缩放的判定（例：窗口这么大该用几号字？鼠标这点落在哪条边上？） | 不能，它是纯计算，运行起来立刻结束 |
| `timer_settings.py` | **记忆** | 把窗口大小/位置/模式/时长写进文件，下次读回来 | 不能，它是被调用的 |
| `timer_ui.py` | **前端** | 界面：画面板、画数字、画按钮，把点击和按键转成对后端的调用 | 不能，它是被 `timer.py` 调用的 |
| `timer.py` | 入口 | 创建窗口、把上面几层装到一起、启动 | **能，就运行它** |

**这几个文件的关系**：`timer.py` 启动时先造一个后端秒表、再造一个前端窗口，然后把两者接起来。类比一下——后端是发动机，`timer_view.py` 是换算表，`timer_settings.py` 是记事本，前端是仪表盘外壳，`timer.py` 是那把点火钥匙。全都得在，但你要拧的只有钥匙。

> `timer_view.py` 和 `timer_settings.py` 是 **v1.1.0 新加的**。你会觉得文件突然变多了，就是这两个。它们都不碰窗口，所以能单独测试——这也是为什么加它们不是把简单事情搞复杂，而是让"颜色算得对不对""设置文件被改坏了会怎样"这类问题能在几毫秒内自动查出来。

`tests/` 文件夹同理，是给程序做体检用的，跑程序完全用不到。删掉它程序照常运行，只是没法跑第九节那套测试了。

### 拆开有什么好处

**依赖方向是单向的**：`timer.py` → `timer_ui.py` → {`timer_view.py`、`timer_settings.py`} → `timer_core.py`。后端完全不知道界面的存在（`timer_core.py` 里没有一行 `import tkinter`），由此得到两点：

1. **能自动测试**。后端不依赖窗口，所以可以塞一个假时钟进去、把"计时 30 秒后暂停"这类场景在几毫秒内验证完，不用真的等 30 秒。这是拆分的最大收益。
2. **能换界面**。将来想做成网页、命令行或者系统托盘图标，后端一行都不用改。

前端也从不自己算时间、也不自己算颜色。每次刷新它只是去问后端"现在多少秒了"，字号和配色则去问 `timer_view`。这样每件事都只有一处实现，不会出现两处逻辑对不上的情况。

### 想读代码的话，按这个顺序

`timer_core.py` → `timer_view.py` → `timer_settings.py` → `timer_ui.py` → `timer.py`，正好是从里到外、从简单到复杂。`timer_core.py` 最短也最独立（不 import tkinter，只有 `State`、`format_hms()`、`Stopwatch`、`Countdown` 几样东西），先读它最容易建立概念；`timer_ui.py` 最长也最麻烦（窗口、透明、四边缩放、拖拽这些坑都在里面），放到最后读。

## 五、操作说明

| 操作 | 按钮 | 快捷键 | 说明 |
| --- | --- | --- | --- |
| 开始计时 | 开始 | `空格` | 秒表模式下从头计时，暂停后按它继续累加；倒计时模式下开始往下数 |
| 暂停 | 暂停 | `空格` | 停住显示，已计的 / 剩的时间都保留 |
| 归零 | 重置 | `R` | 秒表清零；倒计时回到**设定的时长**（也就是"重新来一遍"） |
| 切换模式 | 切换为倒计时 / 切换为秒表 | — | 第三颗按钮，文字跟着当前模式变；计时中切换会先确认一次 |
| 设定倒计时时长 | 倒计时模式下点数字 | — | 弹一个小输入框手填，例如 `05:00`、`1:30:00` 或 `90` |
| 移动窗口 | **拖面板上任意位置** | — | 整块都能拖：空白处、数字上、按钮之间的缝隙里都行 |
| 改变窗口大小 | **拖四条边或四个角** | — | 鼠标移到边上，指针变成双箭头，拖就改尺寸；字跟着缩放 |
| 窗口置顶开关 | — | `T` | 默认就是置顶，按 `T` 切换。界面上没有这个按钮 |
| 退出 | 窗口右上角 × | `Esc` | 关闭程序（计时中会先确认一次） |

`空格` 是"开始 / 暂停"的切换键：计时中按它等于暂停，停止中按它等于开始。

**"开始"和"暂停"是同一颗按钮**：点下去之后它就变成暂停，再点又变回开始，所以永远只用看一颗按钮。这是图片里那个样子，也是它比"两颗按钮各自变灰"更好用的地方——你不需要先判断现在该点哪颗。

**为什么整块都能拖**：窗口够大，数字又只占中间一块，如果只有数字那块能拖，你想挪窗口就得先瞄准。现在面板上随便哪儿按住拖都行。唯一的例外是**刚好压在边缘 6 像素上的那一下**——那里是拉大小用的，所以按在边上拖是改尺寸而不是挪窗口。按钮和右上角的 × 优先于边缘，按上去永远是点按钮/关窗口，不会误判成拉边。

## 六、行为细节

这几点是刻意这样设计的，不是巧合：

1. **暂停后按"开始"是继续计时，不是重新开始。** 比如走到 `00:00:30` 暂停，再按开始会从 30 秒继续往上走；只有"重置"才会归零。
2. **计时精度不受界面刷新影响。** 内部用 `time.monotonic()` 记录起止时刻、用时间差算总时长，而不是每刷新一次加一秒，所以就算程序卡顿或系统繁忙，长时间跑也不会累积误差。用 `monotonic` 而不是 `time()` 是因为后者会被系统对时、时区调整影响，可能让计时倒退。
3. **界面每 100 毫秒刷新一次，但只显示整秒。** 因为 `00:00:00` 的格式没有小数位，不足 1 秒的部分会向下取整——所以在 0.9 秒时看到 `00:00:00`、到 1.0 秒才跳到 `00:00:01`，这是正常的。
4. **重复点击有保护。** 计时中再点"开始"、已停止时再点"暂停"，都会被忽略，不会出现时间跳变或翻倍。
5. **"已暂停"和"就绪"是两个不同的状态。** 即使一秒都没走就暂停，状态也是"已暂停"而不是"就绪"（界面上看不出区别，但第一颗按钮的文字靠它决定）。这一点曾经是缺陷：早期版本从"累计秒数是否为 0"反推状态，而 `time.monotonic()` 在 Windows 上分辨率约 16 毫秒，同一 tick 内开始紧接着暂停会读到完全相同的时钟值、累计秒数为 0，状态就被误判成"就绪"，连带按钮联动一起出错。现在状态由各操作显式维护。
6. **小时位是两位宽，超过 99 小时会自动扩宽**（例如显示 `100:00:00`），不会报错。
7. **空格键在窗口里只有一种含义：开始/暂停，而且只会触发一次。** 这曾是缺陷：Tk 的按钮自带 `<space>` 类绑定（内部是 `tk::ButtonInvoke`），而事件按「控件 → 类 → 顶层」的顺序派发，所以焦点在按钮上时按空格会触发两次——一次全局绑定、一次按钮自己的命令，且后者延迟 100 毫秒才执行（`tk::ButtonInvoke` 里是 `after 100`），表现为"按了空格计时器不动"。v1.0.0 的修法是"在每个控件上再绑一份会 `return "break"` 的同名处理，把这次重复派发截断"。**v2.0.0 起理由变了**：按钮改成自己在画布上画的圆角方块，主窗口里一个 `tk.Button` 都不剩，那个类绑定冲突从源头上不存在了，所以那套"从注册表推导该绑哪些控件"的补丁可以整段删掉。行为不变，代码少了一大截。
8. **关闭窗口时会先取消定时器**（`after_cancel`）再销毁窗口，避免退出时报错。这一点比看上去重要：`destroy()` **不会**自动取消已经排队的定时任务（实测过），不显式取消的话，它们会在窗口消失后才触发，控制台会刷出 `invalid command name "..."`。
9. **拉伸窗口时字号跟着变，不会抖。** 按数字区的宽高各算一个上限、取小的那个，再钳到 20~220 像素。细节见第八节。
10. **无边框是必须的，不是审美选择。** 带系统标题栏的窗口设了透明属性，**整个窗口**（连按钮带标题栏）都收不到鼠标点击——暂停之后就再也点不动开始和重置。最小复现确认过，跟我们的代码无关；换成无边框就正常。代价是无边框窗口在 Windows 上点它**不会自动获得键盘焦点**，所以按下鼠标时会显式抢一次焦点，否则空格、`R`、`T`、`Esc` 会全部失灵。
11. **数字要等数字区量出真实尺寸才画，不猜。** 这曾是缺陷（v1.1.1 修）：窗口刚建出来、还没显示到屏幕上时，各个控件的尺寸都还是 `1×1`，这时算出来的数字中心是 `(1,1)`——整串数字被画在画布的左上角外面，屏幕上只剩右下角一点点，看起来就是"数字被盖住了"。而只要窗口显示出来的尺寸**正好等于**记住的那个尺寸，"尺寸变了才重排"这条判断就会认为无事发生，这个错位就再也没人纠正。现在数字区量出尺寸之前一个数字都不画，刷新循环每一轮都会拿显示区尺寸和"上次是照多大画的"比一次，对不上就补画——所以它会自己长好，不依赖任何事件恰好在正确的时刻到达。
12. **倒计时的四条规则**：归零回到设定时长；数到 0 停在 `00:00:00`、状态落回就绪、**只提醒一次**；数到 0 之后直接点开始会从设定时长重新开始（不做这一步的话，用户在 `00:00:00` 上点开始会什么都不发生，像个坏掉的程序）；运行中切模式会先确认一次（切过去等于把当前这次计时丢掉）。
13. **两种模式各记各的。** 秒表的用时和倒计时的剩余时间互不影响，切走再切回来，各自还是走之前那个数。设置文件里存的 `mode` 只管"下次打开先显示哪种"，不影响这次。

## 七、倒计时怎么用

### 切到倒计时

点第三颗按钮「切换为倒计时」，数字就从 `00:00:00` 变成设定的时长（默认 `00:05:00`）。这时第一颗按钮还是"开始"，点下去就往下数。第三颗按钮的文字变成「切换为秒表」，再点一下就切回来。

### 设定时长：点数字

**在倒计时模式下，点一下数字**，会弹出一个小输入框。已经设过的时长会预填在里面，改完回车即可。

支持三种写法，输入框的提示语里也写了：

| 写法 | 意思 | 例子 |
| --- | --- | --- |
| `分:秒` | 省掉小时位，最常用 | `05:00` = 5 分钟 |
| `时:分:秒` | 完整写法 | `1:30:00` = 1 小时 30 分 |
| 纯数字 | **按秒算** | `90` = 90 秒 |

纯数字按秒而不是按分，是刻意选的：秒是这个程序的基本单位，输入和显示才对得上（输入 `90`，屏幕上是 `00:01:30`）。

输错了不会静默吞掉——会告诉你是哪儿不对（比如「哈哈」不是数字、分钟位要小于 60、时长要大于 0），然后**重新弹一次**输入框，不用从头再点一遍数字。

### 到点会发生什么

三件事一起：响一声系统提示音、面板底色闪几下、弹一个「时间到」的提示框。**只提醒一次**，关掉提示框之后数字停在 `00:00:00`。

这时候直接点"开始"会从设定时长重新数一遍——不用先按重置。

### 运行中切模式会先问你

切过去等于把当前这次计时丢掉，所以会先弹一句确认。点"取消"就什么都不发生，正在跑的还是接着跑。

> 秒表模式下点数字不会有任何事——只有倒计时模式才需要设时长。

## 八、界面是怎么做出来的

### 半透明的深灰面板

窗口整体加了固定的透明度（`-alpha 0.86`），所以能透出底下的软件。数字和按钮画在这层半透明上，颜色选得够亮，看久了也不费劲。

**为什么是"整窗半透明"而不是"把底色整片抹掉"**：v1.1.0 用的是后者（颜色键透明），代价是抹掉的地方鼠标会直接穿透到桌面——窗口有一半抓不住，"窗口拖不动"就是这么来的。整窗半透明没有这个副作用：**窗口上每一处都点得动**，这才有了现在的"整块都能拖"。

### 圆角怎么雕出来的

Tk 画不出圆角窗口，用了一个取巧办法：**把窗口的底色设成一个几乎不会被用到的深紫色 `#010203`（叫"角键"），然后告诉 Windows "凡是这个颜色的像素都算透明"**，再用画布画一块圆角矩形盖在这层底色上。于是四个角上露出的是那层深紫底色，被系统抠掉——看起来就是圆角。

这个把戏只用在四个角上，**面板本体是实心画上去的**，所以不存在"穿透"问题。万一哪天系统不认这一招，退化的结果是**四个角变成直角**，程序照常能用。

### 配色是算出来的，不是配出来的

只有一套配色（深灰面板 + 白字），不需要用户选。但底色的深浅仍然是**算**的：底色深就配白字、浅就配黑字（按 WCAG 标准的相对亮度判断，不是简单取通道平均值），按钮色在底色上提亮一档，另外有一条保险丝——按钮和面板的色差永远不小于一个阈值，免得按钮糊进背景里看不见。

> 数字边缘**没有**明显的灰边。当初担心 Tk 的字体抗锯齿会在字形周围留一圈灰晕，实际做出来在这个字号下基本看不出来（在纯品红/青色这种极端背景上验过）。这条原本是风险项，实测后不成立。

| 字段 | 意思 |
| --- | --- |
| `mode` | 上次用的是哪种：`watch`（秒表）或 `countdown`（倒计时） |
| `target` | 上次设的倒计时时长，单位秒 |
| `width` / `height` | 窗口大小 |
| `x` / `y` | 窗口位置 |

**想恢复出厂设置，就把这个文件删掉**，下次启动会重新按默认值来。

为什么不放在程序旁边：exe 是单文件打包的，程序目录在运行时其实是个临时解压目录，退出就没；而且放进 `C:\Program Files\` 会因为没有写权限而存不进去。`%APPDATA%` 两个问题都没有。

> 这个文件**被改坏了也不会让程序打不开**——读不出来就静默按默认值启动。手动把 `mode` 写成别的词、把尺寸写成负数、甚至把整个文件删成半截，最多是那一项设置失效，其余项照常记住。从 v1.x 升级上来的旧文件里还有 `bg` / `transparent`，会被直接忽略，不用管。

### 窗口缩放是怎么算的

大号数字占面板中间那一整块，字号按**数字区的宽高各算一个上限、取小的那个**，再钳到 20~220 像素。按钮文字按数字字号等比缩放，另有上下限（免得小到点不着或大到撑破按钮）。

字体比例是**启动时实测量出来的**，不是写死的——写死就得猜 Consolas 的字符宽度，而且换台机器字体被替换就全错。

窗口最小 380×220，再小按钮就挤不下了。窗口位置也会记住，但恢复时会先确认那一块还在屏幕里（至少留 90 像素可见），免得上次那块显示器已经拔掉了。

### 拖边改尺寸是怎么算的

鼠标按下时先看落在哪，顺序是：**按钮或 × 上 → 交给控件；否则落在边缘 6 像素带里（四个角是 14 像素）→ 进入"拉边"模式；都不是 → 进入"挪窗口"模式**。

"控件优先"这条是关键：右上角的 × 和底部的按钮行都压在边缘带上，靠这条规则它们才不会被拉边抢走。

拉左边或上边时，对面那条边必须**钉住不动**——所以窗口的左上角坐标得跟着尺寸一起改。这是手写缩放最容易漏的一处，漏了的表现是"拖左边，窗口整个往右跑"，现在有测试专门钉着。

## 十、打包成 exe

只有打包时才需要装 PyInstaller，装进项目虚拟环境（`.venv/` 已在 `.gitignore` 中，不会入库）：

```bash
cd F:\DesktopTimer
python -m venv .venv

.venv/Scripts/python.exe -m PyInstaller --onefile --windowed --name DesktopTimer --clean --noconfirm --noupx timer.py
```

参数含义与取舍：

| 参数 | 作用 | 取舍 |
| --- | --- | --- |
| `--onefile` | 全部打进单个 exe | 便于分发；代价是每次启动要把内置归档解压到临时目录，**首次启动约 1-3 秒**。想要秒开可改成 `--onedir`（产物变成一个文件夹） |
| `--windowed` | 不创建控制台窗口 | GUI 程序必加，否则会多一个黑终端。副作用是出错时的报错信息也看不见了 —— 如果 exe 双击没反应，临时去掉这个参数重新打包就能看到报错 |
| `--name` | 产物名 | 用了英文名，某些杀毒软件和非 ASCII 路径对中文文件名不友好 |
| `--clean` | 清缓存重建 | 避免旧缓存导致"改了代码 exe 没变" |
| `--noupx` | 禁用 UPX 压缩 | 压缩过的 exe 更容易被杀毒软件误报 |

**已知问题**：单文件 exe 的自解压结构是 Windows Defender 的常见误报源（典型名称 `Trojan:Win32/Wacatac.B!ml`）。没有代码签名证书就无法根治，可以给 `dist` 目录加一个 Defender 排除项，或改用 `--onedir`。

**打包产物不进仓库**：`dist/`、`build/`、`*.spec` 都已被 `.gitignore` 忽略。十来 MB 的二进制提交进 git 会让仓库永久变大，且每次重新打包都会产生一整份新副本。

## 十一、常见问题

**Q：提示 `'python' 不是内部或外部命令，也不是可运行的程序`**
说明安装 Python 时没勾选 "Add Python to PATH"。可以改用 Windows 自带的启动器：

```bash
py timer.py
```

**Q：双击后黑框一闪就没了**
说明双击打开的方式把程序当成脚本执行完就退出了，通常是 `.py` 没关联好。改用命令行的方式 1。

**Q：窗口弹出来了，但没有反应 / 按钮点不动**
检查是不是终端里报错了（比如缺少 tkinter）。把终端里的报错信息发出来即可定位。

**Q：怎么设倒计时时长？**
先点第三颗按钮切到倒计时模式，然后**点一下那串数字**，会弹一个小输入框。已设过的时长会预填在里面。写法支持 `05:00`（5 分钟）、`1:30:00`（1 小时 30 分）和 `90`（90 秒）。秒表模式下点数字没有反应，因为秒表不需要设时长。

**Q：拖左边改大小时，窗口整个往右跑了**
那不是 bug 就奇怪了——**拉左边时右边必须钉住不动**，所以窗口左上角的坐标得跟着尺寸一起改。这条有专门的测试钉着（`test_dragging_the_left_edge_keeps_the_right_edge_still`）。如果你真的遇到了，把复现步骤告诉我。

**Q：为什么贴着边拖是改大小，不是挪窗口？**
边缘 6 像素（四个角 14 像素）专门留给拉大小用，这是刻意的——不然无边框窗口就没法改尺寸了。想挪窗口就**往里挪一点再拖**，面板上除了这一圈边都是能拖的。按钮和右上角的 × 优先于边缘，按上去永远是点按钮/关窗口。

**Q：怎么改配色 / 怎么关掉透明？**
v2.0.0 起这两项固定了，界面上没有开关，设置窗也删了。想彻底恢复出厂设置，把设置文件删掉即可（路径见第八节）。

**Q：`pip install` 报 `ValueError: check_hostname requires server_hostname`**
系统代理被 `urllib` 从注册表读到了，且协议头不对：注册表里存的是 `127.0.0.1:7897`（HTTP 代理），但 `urllib` 给 https 自动加上了 `https://` 前缀，于是 pip 试图对代理本身做 TLS 握手。用正确的协议头覆盖即可：

```bash
export HTTPS_PROXY=http://127.0.0.1:7897
export HTTP_PROXY=http://127.0.0.1:7897
```

（PyPI 本身直连可达，不需要代理；这个报错纯粹是注册表代理被误读导致的。）

## 十二、代码接口

每个文件干什么见第二节，这里只列公开的调用接口（想改代码时看这段）。

**后端 `timer_core.py`：**

| 接口 | 说明 |
| --- | --- |
| `Stopwatch(clock=time.monotonic)` | 造一个秒表。`clock` 是时钟，可注入，测试时换成假时钟 |
| `Countdown(clock=..., target=300)` | 造一个倒计时。接口和 `Stopwatch` 完全一样（都满足 `Timer` 这个协议），**所以界面层拿同一个变量驱动，不用到处判断是哪种模式** |
| `.state` / `.is_running()` | 查询状态，返回 `State.IDLE` / `RUNNING` / `PAUSED` |
| `.total_seconds()` / `.formatted()` | 读当前读数，后者直接给 `时:分:秒` 字符串（秒表是已用时间，倒计时是剩余时间） |
| `.start()` `.pause()` `.toggle()` `.reset()` | 四个操作，都返回"本次是否真的改变了状态" |
| `Countdown.set_target(秒数)` / `.target()` | 设 / 读设定的时长。只在没跑的时候允许改 |
| `Countdown.is_finished()` | 是否已经数到 0（界面用它保证"只提醒一次"） |

两个独立的纯函数，前端和界面都靠它们：

| 函数 | 说明 |
| --- | --- |
| `format_hms(秒数)` | 秒数 → `时:分:秒` 字符串 |
| `parse_hms(文本)` | 用户手打的时长 → 秒数。认三种写法（`1:30:00` / `05:00` / 纯数字按秒），**认不出就抛 `ValueError` 并说明原因**，不返回 0 也不返回 `None`——调用方要把原因告诉用户 |

**前端 `timer_ui.py`：** 只有 `TimerApp(root, watch=None, settings_path=None)` 一个类。三个参数都是为了注入——`watch` 不传就自己造一个真秒表，`settings_path` 不传就用 `%APPDATA%` 里那个真实路径（**测试必须传，否则会把你的设置覆盖掉**）。

整个窗口是**一块画布**：面板、数字、三颗圆角按钮、右上角的 × 全都画在同一张画布上。所以"按钮"没有 `tk.Button` 对象，是画上去的圆角矩形 + 文字，鼠标落在哪个矩形里由 `timer_view.panel_layout()` 算出来的坐标决定。

**算法 `timer_view.py`**（零 tkinter）：

| 接口 | 说明 |
| --- | --- |
| `normalize_color(文本)` | 把颜色规范成 `#rrggbb` 小写；认不出就抛 `ValueError` |
| `build_theme(底色)` | 从底色派生出整套配色，返回 `Theme` |
| `Theme` | 值对象，字段：`bg` `fg` `hint_fg` `btn_bg` `btn_fg` `btn_active` `btn_pressed` |
| `relative_luminance(颜色)` | WCAG 相对亮度，0（黑）到 1（白），gamma 校正过 |
| `digit_font_px(数字区宽, 数字区高, 两比例)` | 算大号数字的字号（像素） |
| `scaled_font_px(基准, 比例, 下限, 上限)` | 次要文字的等比缩放 |
| `clamp_window_size(宽, 高)` / `clamp_window_position(x, y, 宽, 高)` | 尺寸钳到合理范围 / 位置钳回屏幕内（至少留 90 像素可见） |
| `stroke_color(字色, 底色)` / `stroke_offsets(半径)` | 数字描边：挑一个跟底色反差最大的颜色，以及要画的 8 个偏移量 |
| **`panel_layout(宽, 高, 三颗按钮的文字宽, 字体高)`** | **核心函数**。算出面板、三颗按钮、右上角 ×、数字区各占哪块矩形，返回 `PanelLayout` |
| `panel_radius(高)` | 圆角半径，跟着窗口高度走，钳在 10~18 像素 |
| `rounded_rect_points(x0, y0, x1, y1, 半径, 步数)` | 圆角矩形的轮廓点，直接喂给画布的多边形图元 |
| **`resize_zone(x, y, 宽, 高, 边宽, 角宽)`** | **点在哪个缩放区**：返回 `'n'` / `'s'` / `'e'` / `'w'` / `'nw'` / `'ne'` / `'sw'` / `'se'`，都不在返回 `None` |
| **`resize_rect(区, 起始尺寸, 起始位置, dx, dy)`** | **按拖了多少像素算新的 `(x, y, 宽, 高)`**。返回 x/y 不是多余的——拉左边时右边要钉住不动，所以左上角坐标必须跟着尺寸一起改 |

**记忆 `timer_settings.py`**：

| 接口 | 说明 |
| --- | --- |
| `Settings` | 值对象：`mode` `target` `width` `height` `x` `y` |
| `load(path=None)` | 读设置。**任何异常都静默退回默认值，绝不抛异常** |
| `save(设置, path=None)` | 原子写（先写临时文件再替换），返回是否成功，**绝不抛异常** |
| `default_path()` | 就是 `%APPDATA%\DesktopTimer\settings.json` |

`load()` 只对**出问题的那个字段**退回默认值，其余字段照常保留——比如手改坏了倒计时时长但尺寸是对的，尺寸应该还能记住。老文件里已经删掉的 `bg` / `transparent` 键会被直接忽略，不需要写迁移代码。

## 十三、可能的后续扩展

目前没有实现、但改动不大的功能：

- **记录多段计时 / 计次**：在数字下方加一个列表显示每次暂停的时间点
- **倒计时到点后自动循环**（番茄钟那种）：现在的行为是数到 0 停住，再点开始才重来
- **标题可编辑**：现在没有标题，标题栏都被去掉了
- **多显示器之间的位置恢复**：现在只保证窗口不跑到屏幕外，不保证还回到上次那块显示器上
- **开机自启 / 系统托盘**：与计时逻辑无关，属于外壳工作
- **换界面**：后端不依赖界面，理论上可以再套一个网页界面或命令行界面

> 这里原来有四条已经在 v1.1.0 / v2.0.0 做掉了：**倒计时模式**（v2.0.0）、**记住窗口位置**（v1.1.0）、**整窗半透明**（v2.0.0）、**保存设置**（v1.1.0）。

> 关于整窗半透明有一条实测警告仍然有效：Tk 只暴露了"整窗均匀变淡"这一种（`-alpha`），**最小只能给到 0.25，绝不能给 0**。实测 `alpha=0.0` 会让整个窗口一起穿透，变成一个看不见、点不到、连 × 都按不中的窗口，只能去任务管理器杀进程。现在这个值是 `WINDOW_ALPHA = 0.86`，写在 `timer_view.py` 里。

## 十四、提交与推送流程

### 手动提交（三步）

```bash
cd F:\DesktopTimer
git add .
git commit -m "描述这次改了什么"
git push
```

想先看看改了哪些文件用 `git status`，想看具体改动用 `git diff`；想撤销某个还没提交的改动用 `git checkout -- 文件名`。

### 让 Claude 代为提交

直接说「**改动描述 + 提交并推送**」，例如"把字体调大了，提交并推送"。

| 说法 | 实际动作 |
| --- | --- |
| 把字体调大了，提交并推送 | 提交 + 推送 |
| 修好了暂停的 bug，提交并推送 | 提交 + 推送 |
| 只提交，先别推送 | 只做本地提交，GitHub 不动 |
| 看看我改了什么 | 只给你看 `status` / `diff`，不动仓库 |
| 推上去 | 用上次说过的改动内容提交并推送 |

约定：

- 提交信息用中文，动词开头一句话说明做了什么，多条改动分点列出
- 只是"提交"而没有说"推送"，**默认只做本地提交**——本仓库是 Public，推送等于公开发布
- 推送前会先把提交信息和将要上传的文件清单报出来
- 建议在描述里说清**为什么改**，而不只是改了什么：`git diff` 只能看出哪几行变了，意图只有你知道，而这决定了提交信息怎么写

### 网络问题（重要）

本机 `github.com` 直连会被重置。浏览器能打开 GitHub 是因为走了系统代理，但 **git 不读取 Windows 系统代理**，所以命令行直连一定失败。本仓库已经把代理写进 `.git/config`：

```
http.proxy = http://127.0.0.1:7897
```

如果某天推送报 `Connection was reset`，多半是代理工具重启后换了端口，按新端口更新即可：

```bash
git config http.proxy http://127.0.0.1:新端口
```

## 十五、发布新版本（打 tag + 发 Release）

### 为什么 exe 不直接提交进仓库

**不要 `git add dist/DesktopTimer.exe`。** 每次迭代都会往仓库里存一份 8 MB 的新副本，而且 git 保留全部历史——以后即使删掉，旧的那几份也还在 `.git` 里，仓库会迅速膨胀到几百 MB，别人 clone 一次要等很久。

正确做法是走 **GitHub Release**：仓库里只存代码和一个 **tag**（钉在某个提交上的名字），exe 作为 Release 的**附件**挂在 tag 上。

```
仓库里存的：代码 + tag
                │
                ├── v1.0.0 ──► Release「v1.0.0」──► 附件 DesktopTimer.exe
                ├── v1.1.0 ──► Release「v1.1.0」──► 附件 DesktopTimer.exe
```

### 发版四步

**第 1 步：改代码，测试通过**

```bash
python -m unittest discover -s tests -t . -v
```

**第 2 步：重新打包 exe**

```bash
.venv/Scripts/python.exe -m PyInstaller --onefile --windowed --name DesktopTimer --clean --noconfirm --noupx timer.py
```

**第 3 步：打 tag 并推送**

```bash
git tag v2.0.0
git push origin v2.0.0
```

tag 打完，v2.0.0 这一刻的代码就被永久记住了，以后随时切回去看：

```bash
git checkout v2.0.0    # 切到 v2.0.0 当时的代码
git checkout main      # 切回最新
```

**第 4 步：在 GitHub 网页上建 Release**

1. 打开 https://github.com/Fairy-Xu-28/DesktopTimer/releases
2. 点 **Draft a new release**
3. **Choose a tag** 下拉里选刚才推上去的 `v2.0.0`
4. **Release title** 填 `v2.0.0`，或写人话如 `v2.0.0 半透明圆角面板 + 倒计时`
5. **Describe this release** 写这次改了什么——这段是给下载的人看的更新日志
6. 把 `dist\DesktopTimer.exe` **拖进**最下方附件区（那里有一行小字 "Attach binaries by dropping them here"）
7. 点 **Publish release**

发布后，任何人在 Releases 页面就能直接下载 exe，不需要懂 Python、不需要装环境。

## 十六、新开一个对话时，可以对我说什么

每次开新对话，我的记忆是空的——不知道你上次改到哪、不知道这个项目是什么。**在 `F:\DesktopTimer` 目录下开对话**，这份 README 会自动读到，我就知道上下文了。

然后照下面这些句子说就行，不用组织语言：

| 你想干什么 | 直接这么说 |
| --- | --- |
| 改点东西 | 把按钮文字改成"开始计时"，改好测试完提交并推送 |
| 只想先看看效果 | 把面板的透明度调高一点，改好先别提交 |
| 修 bug | 按空格有时候秒表不动，查一下修好，提交并推送 |
| 想知道代码怎么回事 | 那个半透明的圆角是怎么做出来的？ |
| 跑一遍检查 | 跑一下测试，告诉我有没有问题 |
| 看改了哪些文件 | 看看我改了什么 |
| 提交但不发布 | 只提交，先别推送 |
| 发新版本 | 发布 v2.0.0 |
| 想不起来该说什么 | 这个项目现在是什么情况？ |

几条能省事的习惯：

- **说清"为什么改"而不只是"改成什么"**。`git diff` 只能看出哪几行变了，意图只有你知道，而提交信息要写的是意图。
- **改动多就分几次说**。一次让我改五件事，中途哪件不满意就得整体回退；分五次说，每件都能单独验证、单独回退。
- **不确定就先问**。像"这个能不能做"这种问题直接问，我不会动手改任何东西。
- **涉及发布的词说清楚**。**"提交"和"推送"是两回事**：本仓库是公开的，推送等于公开发布，所以你没说"推送"我就只做本地提交，不会替你公开。

> 这份清单本身也是可以改的。觉得哪句说法别扭、或者有更顺口的说法，告诉我，我把它更新到这张表里。
